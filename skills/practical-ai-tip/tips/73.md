## 73. Define "Done" as a Condition the Agent Can Check

An agent stops when it thinks the work is good enough. Give it an exact completion condition, and it keeps going until the condition is met.

- **Use when:** a task has a clear finish line.
- **Implementation:**
  1. State exactly what is included, so nothing gets quietly dropped.
  2. State the stop condition and the edge cases, so the agent cannot decide some items do not count.
  3. In Claude Code, run `/goal` with the condition and a cap on tries. Each time the agent tries to stop, a check compares the condition with the work so far.
  4. Leave out lines such as "keep going" or "don't be lazy"; they cause over-work.
  5. If the agent still ends turns before the work is done, for example by listing what is left or offering to continue, add a finishing instruction such as the asset below. In the source's tests, about half as many sessions ended with unfinished work. Keep a confirmation step for risky or irreversible actions.
     > [!info] Sources disagree
     > One source leaves out "keep going" lines because they cause over-work[^ABP]; another adds a finishing instruction for agents that stop early, most often at low or medium effort[^AN-fable52].
- **Asset:** the source's finishing instruction, for the system prompt or the always-loaded instruction file:
  ```
  # Finishing work
  Please avoid stopping while you still owe work the user asked for. Be persistent and do not stop unless needed.

  While status notes are welcome, as is clarifying with the user on open decisions, carry on with work that does not depend on the user's answer without unnecessary stops.

  If you notice yourself inviting the user to redirect you or offering to wait, instead proceed on the next part of the task. You may meet ordinary obstacles like errors, timeouts, locked files, empty results or failing tools. Diagnose them first, and when they are not real blockers, work through them with the access you have (wait and retry, fix the request, use another tool or source) rather than stopping unnecessarily.

  If someone clearly decided something is a hard blocker, such as a file marked not to be touched, access that was intentionally withheld, or a safety guardrail, leave it alone, say plainly what you found, and look for another safe way to finish the task. Stopping before the task is complete is very rarely merited, as in when the task can't move forward without user input, or where the blocker is deliberate and should not be worked past. This does not override the need for confirmation on risky or destructive actions.
  ```
- **Limits:** works best with conditions a machine can check, such as a passing check or a score; the finishing instruction raises output tokens by about 30 percent[^AN-fable52].
- **Requires:** Claude Code, for `/goal`.
